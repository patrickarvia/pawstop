# Pawstop V2.2 API contract

Status: architecture contract for future implementation. This step changes documentation only; it does not implement an endpoint or change the current prototype.

## 1. Product goal

V2.2 replaces the curated Jersey City → Chicago route and six hard-coded stops with real route-aware data while preserving Pawstop's existing scoring and cadence logic.

The pipeline is:

**real origin/destination → real driving route → break targets → real stop discovery → normalized Pawstop data → Pawstop scoring → chronological recommendations**

Google provides route and place data. Pawstop owns normalization, scoring, explanations, and recommendation logic.

## 2. Architecture

```text
Browser → POST /api/plan-route → Pawstop server/serverless function
        → Google Routes + Google Places → Pawstop normalization/scoring
        → normalized JSON response → existing browser UI
```

Google web-service API credentials must remain server-side and never appear in `app.js`, browser responses, or the public repository. Configure credentials in the deployment environment; sanitize provider failures before returning them.

## 3. POST /api/plan-route request contract

Accept `application/json` using provider-independent names. All fields below are required. Origin and destination are trimmed, nonempty text; dog name is display text. `lifeStage` is `puppy`, `adult`, or `senior`. Cadence must be a finite positive number of minutes; maximum detour must be a finite nonnegative number of minutes. Preferences are explicit booleans. Validate types, enums, and reasonable input bounds server-side before calling providers; exact operational bounds belong to implementation.

```json
{
  "origin": "Jersey City, NJ",
  "destination": "Nashville, TN",
  "dogName": "Conan",
  "lifeStage": "puppy",
  "breakCadenceMinutes": 150,
  "maxDetourMinutes": 10,
  "preferences": {
    "largeGrass": true,
    "lowDogTraffic": true,
    "restrooms": true,
    "minimalDetours": true,
    "fencedSpace": false,
    "goodLighting": false,
    "avoidDedicatedReliefAreas": true
  }
}
```

No Google request objects, API keys, or provider-specific preference names are accepted as part of this contract.

## 4. Real route model

Use Google Routes API `computeRoutes` for a driving route. Initial field mask:

```text
routes.duration,routes.distanceMeters,routes.polyline.encodedPolyline
```

Normalize into these Pawstop fields:

| Field | Meaning |
| --- | --- |
| `durationMinutes` | Positive numeric driving duration, converted from provider duration to minutes. |
| `distanceMeters` | Numeric driving distance in meters. |
| `encodedPolyline` | Encoded route geometry used for route-aware discovery. |
| `provider` | Provenance identifier, initially `google`. |
| `trafficAware` | Boolean reflecting the actual routing mode used. |

The browser consumes this normalized model rather than raw Google responses. Keep precision for planning and round only for display. Traffic-aware versus traffic-unaware duration remains an experiment, not a settled default. See Google's [computeRoutes reference](https://developers.google.com/maps/documentation/routes/reference/rest/v2/TopLevel/computeRoutes).

A successful response uses a Pawstop envelope with `route` (the model above), `breakTargetsMinutes` (an ascending numeric array), and `recommendations` (one entry per target). Each entry contains `targetMinutes` and `stop`, where `stop` is the normalized object in section 9 or `null` for an explicit coverage gap. A short route with no targets succeeds with empty arrays. Partial coverage remains a successful plan with visible gaps.

## 5. Break targets

Generate targets from real route duration using the existing cadence model: positive cadence multiples strictly less than arrival time. Do not create a target at or beyond arrival.

```text
route = 812 minutes
cadence = 150 minutes
targets = [150, 300, 450, 600, 750]
```

Targets represent driving time from origin, not wall-clock arrival times. Preserve the current model's exclusion of break duration and time-zone adjustments; cumulative multi-stop itinerary recalculation is not required by this release.

## 6. Real stop discovery

Use Places API (New) Text Search with Search Along Route. Pass route geometry as:

```text
searchAlongRouteParameters.polyline.encodedPolyline
```

Keep initial discovery concepts narrow: parks, recreation areas, picnic grounds, and rest stops. These are search concepts; the exact query/category set remains open. Search bias alone does not establish an acceptable detour: validate route impact before recommending a candidate.

Dog parks and dedicated dog areas may form a separate candidate pool. They receive strong negative treatment when `avoidDedicatedReliefAreas` is enabled. Deduplicate results by Google Place ID before enrichment and ranking. See Google's [Search Along Route guide](https://developers.google.com/maps/architecture/search-along-route-places-and-routes-api).

## 7. Staged candidate enrichment

Do not request expensive or high-detail data for every candidate. Use this pipeline:

1. Discover.
2. Deduplicate.
3. Apply structural filtering, such as valid identity/location and relevant place category.
4. Identify candidates relevant to break targets.
5. Enrich only strong candidates.

Initial discovery data may include `id`, `displayName`, `formattedAddress`, `location`, `primaryType`, and `types`. Selective enrichment may include `allowsDogs`, `restroom`, `parkingOptions`, and `routingSummaries`. Use explicit field masks and verify field availability and cost during implementation. Provider omissions remain unknown.

`routingSummaries` is a response-level routing result, not a Place attribute; associate it with its candidate in the provider adapter. Investigate how to obtain it selectively without enriching the entire discovery pool. Coarse relevance filtering can reduce work, but only actual route metrics may support final timing and detour claims.

## 8. Known / inferred / unknown data model

Every preference-facing attribute carries `{ "value": ..., "confidence": ... }`. Confidence is exactly one of `confirmed`, `inferred`, or `unknown`. An optional `evidence` description records the source or inference basis; confirmed and inferred claims must have supporting evidence available for explanations.

| Attribute | Value | Confidence |
| --- | --- | --- |
| Restrooms | `true` | `confirmed` |
| Large grass | `"likely"` | `inferred` |
| Dog traffic | `null` | `unknown` |
| Fenced | `null` | `unknown` |

**Unknown must not be presented as known. `false != unknown`.** Use `null` with `unknown` for missing evidence; a confirmed `false` means evidence of absence. Confirmed describes supported information, not a guarantee of current conditions. Label inference visibly.

Pawstop must not fabricate dog traffic, grass condition, cleanliness, fencing, lighting, or other attributes without evidence. A park category alone does not confirm large grass, low dog traffic, or permission for dogs. The absence of a dog-park category does not confirm the absence of a dedicated dog area.

## 9. Normalized Pawstop stop schema

The stop object is provider-independent. Provider identifiers belong in provenance; consumers use a stable Pawstop `id`.

| Field | Type / meaning |
| --- | --- |
| `id` | String; stable Pawstop identity. |
| `name` | String; display name. |
| `primaryType` | Normalized Pawstop category string, or `null` if unavailable. |
| `address` | Display address string, or `null` if unavailable. |
| `lat`, `lng` | Valid numeric coordinates for the actual place/access point. |
| `route.tripMinutes` | Numeric driving time from origin to candidate, as defined in section 11. |
| `route.detourMinutes` | Numeric additional driving time attributable to this candidate. |
| `route.targetMinutes` | Assigned cadence target. |
| `route.deltaMinutes` | `tripMinutes - targetMinutes`; negative is early. |
| `route.timingLabel` | Pawstop timing explanation from section 13. |
| `pawstop.matchScore` | Preference match, preserving the current 0–98 scale; not a probability. |
| `pawstop.plannedFitScore` | Match score minus timing penalty; may be negative. |
| `pawstop.why` | Array of evidence-aware explanation strings. |
| `attributes.largeGrass` | Confidence-bearing boolean, `"likely"`, or `null`. |
| `attributes.dogTraffic` | Confidence-bearing `"low"`, `"medium"`, `"high"`, or `null`. |
| `attributes.restrooms` | Confidence-bearing boolean or `null`. |
| `attributes.dogsAllowed` | Confidence-bearing boolean or `null`; disclose access restrictions in evidence. |
| `attributes.fenced` | Confidence-bearing boolean or `null`. |
| `attributes.lighting` | Confidence-bearing boolean or `null`; evidence must support useful lighting. |
| `attributes.parking` | Confidence-bearing boolean or `null`. |
| `attributes.dedicatedDogArea` | Confidence-bearing boolean or `null`. |
| `navigation.googleMapsUrl` | Encoded URL that opens the real place, preferably as a waypoint. |
| `provenance.provider` | Source identifier, initially `google`. |
| `provenance.placeId` | Provider place identifier; nullable for future sources without one. |

All attribute fields use the wrapper from section 8. For example:

```json
{
  "largeGrass": { "value": "likely", "confidence": "inferred", "evidence": "Illustrative documented open-field evidence; not a live place claim." },
  "dogTraffic": { "value": null, "confidence": "unknown" },
  "restrooms": { "value": true, "confidence": "confirmed", "evidence": "Illustrative explicit provider restroom field." },
  "dogsAllowed": { "value": null, "confidence": "unknown" },
  "fenced": { "value": null, "confidence": "unknown" },
  "lighting": { "value": null, "confidence": "unknown" },
  "parking": { "value": null, "confidence": "unknown" },
  "dedicatedDogArea": { "value": null, "confidence": "unknown" }
}
```

This fragment illustrates `attributes`, not a real place record. Returned recommendations must have real, validated route metrics. Candidates lacking these metrics cannot be presented as timed recommendations; expose a coverage gap when necessary. Target-specific fields and planned fit are assigned during planning, after normalization.

## 10. Provider separation

**`scoreStop()` must operate on normalized Pawstop data and must not know or care that Google is the provider.**

Provider-specific parsing happens before Pawstop scoring. The adapter converts categories, durations, amenities, missing values, and provenance into Pawstop models. Scoring accepts normalized attributes, route metrics, and planning preferences; it must not branch on Google field names or identifiers.

## 11. Real tripMinutes and detourMinutes

Test both strategies before locking implementation:

- **Option A: Places `routingSummaries`.** Evaluate origin-to-candidate and candidate-to-destination legs, coverage, consistent routing assumptions, and whether selective retrieval is practical. See Google's [routing summary reference](https://developers.google.com/maps/documentation/places/web-service/reference/rest/v1/RoutingSummary).
- **Option B: targeted Routes calculations with the candidate as a waypoint.** Request the leg-level fields needed for strong candidates in addition to the initial route field mask; measure the first leg and total waypoint-route duration.

Conceptual detour:

```text
duration(origin → candidate → destination) - duration(origin → destination)
```

`tripMinutes` is the driving duration from origin to the candidate, including its outbound access leg. It excludes break dwell time and previous recommended stops' detours, preserving the existing origin-based planning timeline. Do not add the full round-trip detour again to this arrival metric. `detourMinutes` measures total route impact relative to the baseline route, not merely time to reach the place.

Use consistent driving, traffic, departure-time, and route options for comparable calculations. Investigate negative or inconsistent deltas rather than silently claiming a negative detour as a benefit. Do not use straight-line distance as a detour proxy. Choose the final method based on correctness, cost, latency, and ability to calculate both trip position and route impact.

## 12. Existing Pawstop scoring to preserve

Preserve these signals:

- Large grass, low dog traffic, restrooms, minimal detours, fenced space, and good lighting.
- Avoid dedicated dog-relief areas, with strong negative treatment for evidenced dedicated areas when selected.
- Max-detour penalty: ten match points plus six per excess minute, even when minimal detours is disabled. This remains a penalty, not a hard exclusion.
- Puppy / Adult / Senior soft signals: puppies favor lower expected dog traffic when supported; adults are neutral; seniors favor smaller detours. These are product preferences, not medical advice.
- Chronological selection and each stop used at most once.

Preserve the half-cadence candidate window, strictly increasing selected `tripMinutes`, and explicit coverage gaps. Rank eligible candidates by planned fit, then absolute timing difference, then detour, as V2.1.1 does.

Refactor `scoreStop()` to handle unknown values correctly. Unknown should neither receive positive evidence nor automatically become a confirmed negative. Exact handling of score denominators, inferred evidence, and confidence weighting remains unresolved pending experiments. Preserve the intent of current scoring while adapting its demo ratings to normalized evidence; do not fill missing ratings with invented values. Explanations must use the same evidence rules as scoring.

## 13. Preserve V2.1.1 planned timing

Real `tripMinutes` must feed the existing rule:

```text
delta = tripMinutes - targetMinutes
±15 minutes = no penalty
Early beyond 15 min: 0.20 points/min
Late beyond 15 min: 0.75 points/min
penalty = max(0, abs(delta) - 15) × (delta < 0 ? 0.20 : 0.75)
plannedFitScore = matchScore - penalty
```

For example, 30 minutes early costs 3 points; 30 minutes late costs 11.25 points. Keep `timingLabel()` behavior: within ±15 minutes is “Close to planned break”; otherwise show minutes early or after the planned break. Labels may round for display without changing penalty calculations.

## 14. Navigation

Pawstop remains a recommendation/planning product, not turn-by-turn navigation. Planned navigation should open Google Maps with **origin → Pawstop stop → final destination** when practical. Use the real place identity or coordinates and appropriate access point; never retain a demo address. If a full waypoint handoff is impractical, open directions to the real stop and make that limitation clear.

## 15. Error contract

Return a normalized JSON error envelope with a stable code and friendly Pawstop message:

```json
{
  "error": {
    "code": "ROUTE_NOT_FOUND",
    "message": "We couldn't find a drivable route between those locations."
  }
}
```

| Code | HTTP status | Meaning |
| --- | --- | --- |
| `INVALID_INPUT` | 400 | Invalid or missing request fields. |
| `ROUTE_NOT_FOUND` | 422 | No drivable route could be resolved. |
| `NO_STOP_CANDIDATES` | 422 | Targets exist, but no usable route-aware candidates remain. |
| `PROVIDER_ERROR` | 502 | Provider failure or unusable provider response. |
| `RATE_LIMITED` | 429 | Request cannot proceed because of rate limiting. |

Raw provider errors must not be exposed to the user. Partial stop coverage is a successful response with gaps; zero targets is also a successful response, not `NO_STOP_CANDIDATES`. Distinguish unavailable provider data from a successful search returning no candidates.

## 16. V2.2 backend scope

Required: input validation, Routes call, Places call, normalization, real route metrics, Pawstop scoring/planning, and normalized errors.

Explicitly out of scope: accounts, authentication, database, saved dogs, saved trips, community submissions, reviews, AI summaries, weather, in-app map, turn-by-turn navigation, native app, and background location. Existing demo observations must not be represented as evidence about newly discovered places.

## 17. V2.2.1 follow-up

Future `POST /api/find-stop-ahead` will use real device location and the remaining route for the urgent-stop experience. Live urgent geolocation does not block V2.2. Do not equate planned origin-based `tripMinutes` with a live urgent ETA; any retained urgent demo must remain clearly identified as a demo until this follow-up replaces it.

## 18. Implementation phases

1. **Real route foundation:** validated request, server-side Routes call, normalized route, real-duration break targets.
2. **Real stop discovery:** narrow along-route searches, deduplication, structural filtering, staged enrichment.
3. **Route-aware trip/detour metrics:** compare both strategies and validate actual candidate timing and route impact.
4. **Pawstop scoring with unknown-data handling:** normalized inputs, evidence-aware matching/explanations, preserved cadence and late penalties.
5. **Loading/error/no-results/product polish:** friendly states, gaps, navigation, visible uncertainty, existing visual identity, and eventual configuration documentation.

## 19. Definition of done

1. Any reasonable real origin/destination can replace Jersey City/Chicago.
2. Route duration and distance are real.
3. Break targets come from real duration.
4. Stops come from real places along that route.
5. Real-route recommendations do not depend on the old six-stop dataset.
6. `tripMinutes` and detours are real route-aware values.
7. Preferences materially affect results.
8. V2.1.1 late-stop timing behavior remains.
9. Unknown attributes remain visibly unknown.
10. Navigate opens the real place.
11. Provider/API failures have friendly Pawstop states.
12. No Google secret appears client-side or in GitHub.
13. `scoreStop()` contains no Google-specific logic.
14. Existing Pawstop visual identity is preserved.
15. README eventually documents configuration and limitations during implementation; the current README is unchanged in this documentation branch.

## 20. Required test routes

- Jersey City, NJ → Chicago, IL.
- Jersey City, NJ → Nashville, TN.
- New York, NY → Boston, MA.
- One short route producing zero or one planned break, such as Jersey City, NJ → Newark, NJ with a 150-minute cadence; confirm actual duration when testing.

For each applicable route, test route resolution, plausible duration/distance, correct break targets, along-route candidates, chronological ordering, real detours, late penalties, preference changes, unknown-data handling, and navigation. Include zero-target success, sparse coverage gaps, no usable candidates, and provider failures. Use controlled timing cases to verify penalties at ±15 minutes and beyond when live routes do not naturally exercise those boundaries. Verify that changing route inputs changes the discovered route and candidate set instead of relabeling the old dataset.

## 21. Open implementation decisions

Keep these unresolved pending experiments:

- Traffic-unaware versus traffic-aware route duration.
- Places `routingSummaries` versus targeted Routes calls.
- Exact discovery query/category set.
- Unknown-attribute scoring policy.
- Conservative large-grass inference rules.

Experiments must respect the fixed boundaries above: real route metrics, no invented attributes, no automatic unknown-as-false conversion, preserved asymmetric timing penalties, and provider-independent scoring.

## 22. Migration from V2.1.1

The existing `const stops = [...]` and `const tripDuration = 780` will eventually be replaced by `/api/plan-route` data. Preserve/adapt:

- `scoreStop()` for normalized evidence and unknown values.
- `plannedTargets()` for the real route duration.
- `plannedTimingPenalty()` for unchanged asymmetric timing costs.
- `planStops()` for chronological, unique-stop selection and gaps.
- `timingLabel()` for real timing differences.
- `reason()` for evidence-aware explanations.
- `navUrl()` for real-place and waypoint navigation.

Desired flow:

```text
Google response → normalizeProviderData() → Pawstop models
                → scoring/planning → existing UI
```

Move/adapt planning responsibilities to the server boundary described above, with the browser rendering normalized results. This document does not modify `app.js`, `index.html`, `style.css`, or the current README.

## 23. Future-provider principle

OpenStreetMap, government park data, highway datasets, and Pawstop community data should eventually map into the same normalized model without rewriting the recommendation engine. New adapters must preserve confidence, provenance, and route-metric semantics. These are future integrations, not additional V2.2 implementation requirements.
